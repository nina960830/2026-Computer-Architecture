# CP3 — AVG 的語意規格、編碼與指令數比較

> 程式碼：`1013/rv32im/`（`test_avg.S` 為 RV32IM baseline，`test_avg_ci.S` 為自訂指令版）
> 量測工具：`rv32im_sim.py` v1.0（自製 RV32IM 組譯器＋指令階層模擬器），Python 3.13.14

## 1. 本次目標

把 AVG 定義成可實作的自訂指令：寫出正式語意、依 §4 的 R-type 格式編碼、
用 3 組範例（含邊界值）驗證機器碼，並量出「有無自訂指令」的指令數差異。

## 2. 設計內容

### 2.1 語意規格（虛擬碼）

**高階語意**

```
function AVG(rs1, rs2):
    s  ← sign_extend(rs1, 33) + sign_extend(rs2, 33)   # 33-bit，不會溢位
    rd ← s >> 1                                        # 算術右移 = floor
    return rd
```

**硬體等價式**（§6.1 的提示，可省掉 33-bit 加法器）

```
rd ← (rs1 & rs2) + ((rs1 ^ rs2) >>> 1)     # >>> 為算術右移
```

兩式結果相同；後者只需 32-bit 資料通路，是 CP4 之後實作 datapath 時要用的形式。

| 項目 | 內容 |
|---|---|
| 運算元 | 二元，`rs1`、`rs2` 為有號 32-bit |
| 定義域 | `[−2³¹, 2³¹−1]` |
| 結果範圍 | `[−2³¹, 2³¹−1]`（證明見 §2.3 的 5 Whys） |
| 溢位處理 | 只有**中間值**需要 33-bit；結果不需要飽和、不需要旗標 |
| 例外 | 無（不產生 trap，不設旗標） |

### 2.2 編碼

依 §4，自訂指令一律 R-type、opcode `0001011`：

```
 31      25 24   20 19   15 14  12 11    7 6       0
+----------+-------+-------+------+-------+---------+
|  funct7  |  rs2  |  rs1  |funct3|  rd   | 0001011 |
+----------+-------+-------+------+-------+---------+
```

| 欄位 | 值 | 說明 |
|---|---|---|
| `opcode` | `0001011` (0x0B) | custom-0（規範固定） |
| `funct3` | `000` | 教師分配，**已確認**（全 0） |
| `funct7` | `0000000` | 教師分配，**已確認**（全 0） |
| `rs1` (19:15) | 暫存器編號 | 第一個運算元 |
| `rs2` (24:20) | 暫存器編號 | 第二個運算元 |
| `rd` (11:7) | 暫存器編號 | `floor((rs1+rs2)/2)` |

設計上的三個決定：

1. **只用 R-type，不做 immediate 版本** — §4 規定所有自訂指令都是 R-type；
   而且 AVG 的兩個運算元地位對稱，沒有「哪一個該當 immediate」的自然選擇。
2. **`funct3`/`funct7` 寫成常數** — 教師分配的是 `funct3 = 000`、`funct7 = 0000000`
   （全 0），仍集中成 `rv32im_sim.py` 的 `AVG_FUNCT3` / `AVG_FUNCT7` 兩個常數，
   日後規格變動只改兩行。
3. **不設溢位旗標** — 結果必然落在 32 位內，理由見 §2.3。

### 2.3 關鍵決策的 5 Whys（§7.4）

> 為什麼 AVG 不需要溢位旗標或飽和邏輯？

1. **為什麼不需要？** 因為 `rd` 一定落在 `int32` 範圍內。
   *可驗證*：12 組測資（含 `INT_MIN+INT_MIN`、`INT_MAX+INT_MAX`）結果都在範圍內。
2. **為什麼一定在範圍內？** 因為平均值必介於兩個運算元之間，而運算元都在 `int32` 內。
   *可驗證*：`min(a,b) ≤ (a+b)/2 ≤ max(a,b)` 對實數成立。
3. **為什麼 `floor` 後不會掉出範圍？** 因為 `floor` 只會往下移不到 1，而 `min(a,b)` 是整數，
   所以 `floor((a+b)/2) ≥ min(a,b)`。
   *可驗證*：`(−3,−4)` → `−4 = min`；`(7,8)` → `7 = min`。
4. **那為什麼 §6.1 還要規定 33-bit？** 因為需要 33-bit 的是**中間的和**，不是結果。
   *可驗證*：`INT_MAX + INT_MAX = 2³²−2` 需要 33 位，但除以 2 後只有 32 位。
5. **所以硬體可以省掉什麼？** 可以省掉飽和電路與溢位旗標，但**不能**省掉第 33 位；
   正解是用 `(a&b) + ((a^b)>>>1)` 讓第 33 位根本不出現。
   *可驗證*：CP2 的 `avg_bits` 5 條指令即為此式的軟體版本。

### 2.4 三個範例（含邊界值）

| # | 指令 | rs1 | rs2 | rd | 機器碼 | 欄位（funct7 / rs2 / rs1 / funct3 / rd / opcode） |
|---|---|---|---:|---:|---:|---|---|
| 1 | `avg a0, a1, a2` | 7 | 8 | 7 | `00C5850B` | `0000000` / `01100` / `01011` / `000` / `01010` / `0001011` |
| 2 | `avg t0, t1, t2` | −3 | −4 | −4 | `0073028B` | `0000000` / `00111` / `00110` / `000` / `00101` / `0001011` |
| 3 | `avg s0, s1, s2` | 2147483647 | 2147483647 | 2147483647 | `0124840B` | `0000000` / `10010` / `01001` / `000` / `01000` / `0001011` |

二進位展開（範例 3，邊界值）：

```
0000 0001 0010 0100 1000 0100 0000 1011
└funct7┘ └rs2─┘ └rs1─┘ └f3┘ └─rd─┘ └opcode┘
0000000  10010   01001   000   01000   0001011
          s2      s1             s0
```

- 範例 1：和為 15（奇數），`floor(15/2) = 7`
- 範例 2：和為 −7（負奇數），`floor(−3.5) = −4`；若照 C 的「向 0 截斷」會得到 −3
- 範例 3：**邊界值**，和為 `2³²−2`，需要 33-bit；32-bit `add` + `srai` 會得到 −1

這三組機器碼不是手算的，是用 `rv32im_sim.py --dump` 組譯出來的；三組結果也由模擬器執行驗證。

### 2.5 硬體實作對應（CP4 之後）

`avg_bits` 的資料通路就是 AVG 指令的 ALU：

```
rs1 ──┬── AND ──────────────┐
      │                     ├── ADD ── rd
rs2 ──┴── XOR ── >>>1 ──────┘
```

- 一條 AVG 指令 = 1 個 AND、1 個 XOR、1 個 33-bit 算術右移（實際是接線）、1 個 32-bit 加法
- 關鍵路徑比一般 `ADD` 多一層（AND/XOR 平行 → 右移是接線 → ADD），
  所以時脈週期不會比 `ADD` 長太多；這是選 `avg_bits` 當硬體形式的理由
- 不需要飽和單元、不需要溢位旗標、不需要多週期

## 3. 結果與分析

> 計數方法：**動態**（模擬器逐條執行，記錄每個 pc 的執行次數）與**靜態**（組譯後 `.text` 的指令字數）分開列表。
> 工具：`rv32im_sim.py` v1.0，Python 3.13.14，Windows 11。不使用 cycle 數（§5.4）。

### 3.1 靜態指令數

| 項目 | RV32IM baseline | 自訂指令版 | 差異 |
|---|---:|---:|---:|
| 單次計算函式 | 5（`avg_bits`） | 2（`avg` + `ret`） | −60% |
| 迴圈函式 | 14（`avg_loop`） | 11（`avg_loop_ci`） | −21% |
| 整個測試程式 `.text` | 100 | 53 | −47% |

### 3.2 動態指令數

| 情境 | RV32IM baseline | 自訂指令版 | 差異 |
|---|---:|---:|---:|
| 12 組測資（每次呼叫含 `ret`） | 60 | 24 | **−60%** |
| 16 元素迴圈 | 194 | 146 | **−24.7%** |
| └ 每元素 | 12 | 9 | −25% |
| └ 扣除 load/store/迴圈控制後的 AVG 本體 | 4 | 1 | −75% |

**每元素的 9 條**（`avg_loop_ci`）：

| 類別 | 條數 |
|---|---:|
| load（2 個輸入） | 2 |
| **`avg`** | **1** |
| store（1 個輸出） | 1 |
| 迴圈控制（4 個 `addi`） | 4 |
| 分支（`bnez`） | 1 |
| **合計** | **9** |

### 3.3 分支數

| 項目 | baseline | 自訂指令版 |
|---|---:|---:|
| 純量實作（12 次呼叫） | 0 分支 / 12 跳躍 | 0 分支 / 12 跳躍 |
| 迴圈（n=16） | 17 分支 / 1 跳躍 | 17 分支 / 1 跳躍 |
| 分支密度（迴圈） | 17 / 194 = 8.8% | 17 / 146 = **11.6%** |

自訂指令**不改變分支數**，只是把迴圈本體變短，所以分支密度反而上升。
這是 CP4 之後討論 pipeline 時要注意的：分支比例變高，branch penalty 的相對成本會變大。

### 3.4 加速比（以指令數計）

> 這裡的「加速比」= baseline 動態指令數 ÷ 自訂指令版動態指令數，**不是實測時間**。
> §5.4 本次不要求 cycle 數，所以下表是時間加速的**上限**，前提是 CPI 與時脈都不變。

| 情境 | baseline | AVG 指令 | 指令數比 | 省下 |
|---|---:|---:|---:|---:|
| 單次計算（inline，不呼叫） | 4 | 1 | **4.0×** | 75% |
| 單次函式呼叫（含 `ret`） | 5 | 2 | **2.5×** | 60% |
| 12 組測資（動態合計） | 60 | 24 | **2.5×** | 60% |
| 16 元素迴圈（動態合計） | 194 | 146 | **1.33×** | 24.7% |
| └ 每元素 | 12 | 9 | **1.33×** | 25% |
| 每元素理論上限（AVG 完全免費） | 12 | 8 | 1.5× | 33% |

**為什麼迴圈只有 1.33×**：每個元素的 12 條裡只有 4 條是 AVG 本體。

```
baseline : 2 load + 4 AVG + 1 store + 4 addi + 1 bnez = 12
                    └── 換成 1 條 ──┘
自訂指令 : 2 load + 1 avg + 1 store + 4 addi + 1 bnez =  9
```

即使 AVG 變成 0 條，每元素也只能降到 8 條（1.5×）。也就是說 12 條裡有 8 條是
記憶體存取與迴圈控制，**只加速 1/3 的部分，整體上限就是 1.5×**（Amdahl 定律）。

**兩個必須講清楚限制**

1. **指令數比 ≠ 時間加速**。時間 = 指令數 × CPI × Tclk；本節只量了第一項。
   說「快 1.33 倍」時，正確的說法是「指令數少 25%，時間加速上限 1.33 倍」。
2. **自訂指令可能拉長時脈週期**。AVG 的關鍵路徑是 `AND/XOR → 右移（接線）→ ADD`，
   比一般 `ADD` 多一層。若做成 single-cycle，`Tclk` 變長會吃掉部分收益，
   實際加速可能低於 1.33×；要等 CP4 接上 datapath 才能給真數字。

**一句話版本**：單次呼叫快 2.5 倍（5→2 條），放進真實迴圈只有 1.33 倍（12→9 條），
因為每個元素有 8 條是搬資料與迴圈控制，自訂指令省不到。

### 3.5 討論：要靠近上限，必須連周邊一起改

§3.4 的結論是「周邊指令主導」。如果只把 AVG 換掉，最多拿到 1.33×；
要提高，就得同時壓低那 8 條周邊指令。以**展開 2 次 + 位移定址**為例
（以下為依 listing 計數的**估算**，尚未實作量測）：

| 每 2 個元素 | baseline | 自訂指令 |
|---|---:|---:|
| 2 ×（2 load + AVG 本體 + 1 store） | 14 | 8 |
| 共用 overhead（3 個 `addi` + 1 個 `addi` 計數器 + `bnez`） | 5 | 5 |
| 合計 | 19 | 13 |
| 每元素 | 9.5 | 6.5 |

估算加速比 = 19 / 13 = **1.46×**，已經接近 1.5× 的上限。
要再往上就只剩兩條路：減少記憶體存取次數（向量化的 load/store）或加大展開倍數，
兩者都超出「換一條指令」能處理的範圍。

這也是 CP4–CP6 評估加速比時的前提：**自訂指令的效益不是固定的倍數，
而是由它在迴圈裡佔的比例決定**。同一個 AVG，在 unrolled 的純暫存器程式碼裡是 4×，
在記憶體密集的迴圈裡只有 1.33×。

## 4. 遭遇的問題與解法

**問題 1：`funct3` / `funct7` 由教師分配，不能自己選。**

規範說「由教師分配，不可自行更改」。先把兩個欄位集中成 `AVG_FUNCT3` / `AVG_FUNCT7`
兩個常數（`rv32im_sim.py` 開頭），以最保守的全 0 當工作值。分配結果確認後是
**`funct3 = 000`、`funct7 = 0000000`（全 0），與工作值相同，所有機器碼不需重算**。
常數化的寫法保留，日後若規格再變動只改兩行。

**問題 2：Ripes 預設不認識 AVG 指令，怎麼驗證？**

`opcode = 0001011` 不在 RV32IM 標準之內，現成的模擬器不會執行它。驗證改成三層：

1. 自製模擬器解碼 `0001011` 並執行（`test_avg_ci.S` 的 12 組 + 16 元素全部通過，`a0 = 0`）
2. 與 RV32IM 版本**共用同一組測資**（`test_avg.S` 與 `test_avg_ci.S` 的 `.data` 完全相同）
3. 3 組範例（§2.4）手算核對

**問題 3：期望值不能用 C 的 `/` 算。**

C 的整數除法向 0 截斷，`(−7)/2 = −3`，但規格要求 `−4`。所以模擬器的 AVG 語意直接寫成
`(sext(rs1) + sext(rs2)) // 2`——Python 的 `//` 就是 floor。這一點在 CP2 已在 C baseline
上用「負奇數補 1」處理過，兩邊結果一致。

**問題 4（真實踩到）：UTF-8 BOM 讓組譯器把 `\ufeff` 當成助憶符。**

在 Windows PowerShell 用 `Set-Content -Encoding utf8` 產生的 `.S` 帶 BOM，組譯時出現
`unsupported mnemonic '\ufeff'`。解法是在 `assemble()` 讀檔後對第一行做
`lstrip("\ufeff")`。這件事本身也說明：自製工具必須對「Windows 存的檔案」有容錯。

## 5. 白話說明（200 字內）

AVG 就是「兩個數的平均，小數點以下無條件捨去」。麻煩的地方只有一個：兩個 32 位數相加，
結果可能多出一位，直接丢掉就會算錯。我們的解法是換個寫法——「兩數都有的位」加上
「兩數不同的位除以二」，這樣就永遠不會進位，用一條指令就夠。

把它做成一條指令的好處是：原本要五條，現在只要一條。但真正跑一個迴圈時只快了 25%，
因為大部分時間都花在把資料搬進搬出，而不是算平均。

卡住的地方是「平均值的結果需不需要額外的溢位保護」——查了範圍才確定不需要，
要保護的只有中間的和。
