# CP2 — AVG 的 RV32IM 實作與指令統計

> 程式碼：`1013/rv32im/`（對應規範 §5.4 的 `src/rv32im/`）
> 量測數據：`1013/rv32im/counts.md`（由 `rv32im_sim.py` 執行後產生，非手算）

## 1. 本次目標

把 CP1 的 C baseline 改寫成 RV32IM 組合語言，在不使用 64 位元指令的前提下實作
`rd = floor((rs1 + rs2) / 2)`（中間值需 33-bit、不得溢位），並量出各實作的
靜態／動態指令數與分支數，作為 CP3 與自訂指令比較的基準。

## 2. 設計內容

### 2.1 語意與三個約束

| 約束 | 來源 | 影響 |
|---|---|---|
| `rs1 + rs2` 需要 33-bit，不可溢位 | HOMEWORK §6.1 | 不能直接 `add` 後移位 |
| 結果是 **floor**，負數往 −∞ 取整 | §6.1 | 不能沿用 C 的「向 0 截斷」 |
| 只能用 RV32IM | 課程進度 | 沒有 64-bit 指令可用，只能自己處理進位 |

### 2.2 四個實作

| 標籤 | 指令數（含 `ret`） | 正確 | 做法 |
|---|---:|---|---|
| `avg_naive` | 3 | ✗ | `add` + `srai`，直接對 32-bit 結果移位 |
| `avg_wide` | 10 | ✓ | 64-bit 風格：兩個符號位 + 進位組成高位字 |
| `avg_shift` | 7 | ✓ | `(a>>1) + (b>>1) + ((a&b)&1)` |
| `avg_bits` | 5 | ✓ | `(a&b) + ((a^b)>>1)`（§6.1 的硬體提示，最短） |

**`avg_naive`（錯誤示範）**

```asm
avg_naive:
        add   a0, a0, a1        # 只保留低 32 位
        srai  a0, a0, 1
        ret
```

`add` 會把第 33 位丟掉。`INT_MAX + INT_MAX = 2^32 − 2` 繞回 `−2`，`−2 >> 1 = −1`，
但正確答案是 `INT_MAX`。這版的價值是當對照組：它最短，但只在 2 組測資上錯。

**`avg_wide`（安全但冗長）**

```asm
avg_wide:
        srai  t0, a0, 31        # 0 或 -1（rs1 的符號）
        srai  t1, a1, 31        # 0 或 -1（rs2 的符號）
        add   t2, a0, a1        # 和的低 32 位
        sltu  t3, t2, a0        # 32-bit 加法的進位
        add   t4, t0, t1        # 高位字 = 兩個符號位
        add   t4, t4, t3        #         + 進位
        slli  t4, t4, 31        # 高位字的最低位 → 結果的 bit 31
        srli  t2, t2, 1
        or    a0, t2, t4
        ret
```

把 `{t4, t2}` 當成 64-bit 和，右移一位後只有 `t4` 的 bit 0 會落在結果的 bit 31，
所以 `t4` 其餘位元可以不管。

**`avg_shift`（拆移位）**

```asm
avg_shift:
        srai  t0, a0, 1
        srai  t1, a1, 1
        add   t0, t0, t1        # (a>>1) + (b>>1)
        and   t2, a0, a1
        andi  t2, t2, 1         # 兩個人都奇數時才是 1
        add   a0, t0, t2
        ret
```

因為算術右移就是 floor 除法，`a = 2*(a>>1) + (a&1)`，所以
`floor((a+b)/2) = (a>>1) + (b>>1) + ((a&1)+(b&1))/2`，
而 `(a&1)+(b&1)` 只有 0、1、2 三種值，除以 2 就是「兩個都是 1」= `(a&b)&1`。
每一項都落在 `int32` 範圍內，不會溢位。

**`avg_bits`（最短正確版）**

```asm
avg_bits:
        and   t0, a0, a1
        xor   t1, a0, a1
        srai  t1, t1, 1
        add   a0, t0, t1
        ret
```

`(a+b) = (a&b) + (a^b)`，而且 `(a^b)` 的最低位一定是 0（同一位元兩數相同才會是 0），
所以 `(a^b)>>1` 可以直接在 32 位內算，不需要進位；最後的 `add` 也不會溢位。

### 2.3 迴圈版（每元素成本）

```asm
avg_loop:                       # a0 = dst, a1 = src_a, a2 = src_b, a3 = n
        beqz  a3, loop_done
loop_body:
        lw    t0, 0(a1)         # 2 load
        lw    t1, 0(a2)
        and   t2, t0, t1        # 4 條 AVG 本體
        xor   t3, t0, t1
        srai  t3, t3, 1
        add   t2, t2, t3
        sw    t2, 0(a0)         # 1 store
        addi  a1, a1, 4         # 4 條指標／計數器
        addi  a2, a2, 4
        addi  a0, a0, 4
        addi  a3, a3, -1
        bnez  a3, loop_body     # 1 分支
loop_done:
        ret
```

每元素 **12 條**，其中只有 4 條是 AVG 本體。這個比例是 CP3 的主要論點。

### 2.4 ABI 與暫存器

- 參數 `a0`、`a1`，回傳 `a0`，返回位址 `ra`（ilp32）
- 只破壞 `t0`–`t4`，`s0`–`s7` 由呼叫者保存，不建 stack frame
- `ret` 展開成 `jalr x0, 0(ra)`：算「跳躍」不算「分支」，後面統計會分開列

### 2.5 驗證方法

| 項目 | 方法 |
|---|---|
| 12 組功能測資 | 10 組沿用 CP1 `1013/README.md`，另加 `0+0` 與 `INT_MIN+0` |
| 隨機／邊界 | 300 組，其中 1/5 從邊界集合 `{INT_MIN, INT_MIN+1, −1, 0, 1, INT_MAX−1, INT_MAX}` 抽 |
| 期望值 | Python 的 `(a+b)//2`（`//` 就是 floor，與規格一致） |
| 指令數 | 自製 RV32IM 組譯器＋指令階層模擬器，直接執行 `test_avg.S` 的**機器碼** |

本機沒有 `riscv64-elf-gcc`、也沒有任何 C 編譯器，所以指令數不是用 `objdump` 數的，
而是用 `rv32im_sim.py`（v1.0，Python 3.13.14）把 `.S` 組譯成機器碼後逐條執行、
記錄每個 pc 的執行次數。因為是對**機器碼**解碼執行，編碼寫錯會直接反映成錯誤結果，
不會出現「計數正確但程式其實是錯的」情況。另附 `--selftest` 用已知編碼驗證組譯器
（`addi`、`jalr`、`lw`、`sw`、`beq`、`srai`、`sltu`、`lui` 共 9 條）。

### 2.6 關鍵決策的 5 Whys（§7.4）

> 為什麼最後選 `avg_bits`（5 條）而不是 `avg_wide`（10 條）？

1. **為什麼 `avg_wide` 要多花 2 條 `srai` 取符號？** 因為要先把兩個運算元擴充成 64 位才能安全相加。
   *可驗證*：`avg_wide` 原始碼第 1、2 行。
2. **為什麼要擴充成 64 位？** 因為 32 位加法會丟掉第 33 位。
   *可驗證*：`avg_naive(INT_MAX, INT_MAX)` 得到 `−1`，正確值是 `2147483647`。
3. **為什麼會丟掉？** 因為 `add` 只寫回低 32 位，進位沒有地方放。
   *可驗證*：RISC-V `ADD` 的定義，結果取 mod 2^32。
4. **為什麼不另外把進位存起來就好？** 因為進位不等於 33-bit 和的符號位——我們真的這樣寫過，`−10 + 3` 得到 `2147483644`（見 §4）。
   *可驗證*：`--func` 重跑即得。
5. **那能不能一開始就不要產生第 33 位？** 可以：把 `a+b` 改寫成 `(a&b) + (a^b)`，後者最低位必為 0，移位後不會產生進位。
   *可驗證*：300 組隨機／邊界測資 0 失敗。

## 3. 結果與分析

### 3.1 正確性

| 實作 | 12 組測資失敗 | 300 組隨機失敗 |
|---|---:|---:|
| `avg_naive` | 2 | 80 |
| `avg_wide` | 0 | 0 |
| `avg_shift` | 0 | 0 |
| `avg_bits` | 0 | 0 |

測試程式結束時 `a0 = 0`（正確版本零失敗）、`s2 = 2`（naive 的失敗數）。
naive 失敗的兩組正是 `INT_MAX+INT_MAX` 與 `INT_MIN+INT_MIN`。

### 3.2 靜態指令數

| 實作 | 靜態 | 相對 naive |
|---|---:|---:|
| `avg_naive` | 3 | 100% |
| `avg_wide` | 10 | 333% |
| `avg_shift` | 7 | 233% |
| `avg_bits` | 5 | 167% |
| `avg_loop` | 14 | — |
| `_start`（測試主程式） | 61 | — |
| **`.text` 合計** | **100** | — |

> `_start` 的 61 條含 `la`／`li` 展開（`la` = `auipc` + `addi` 共 2 條），
> 是虛擬指令展開後的實際字數。

### 3.3 動態指令數（跑完 12 組測資）

| 函式 | 呼叫次數 | 動態 | 每次呼叫 | load | store | ALU | 跳躍 | 分支 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `avg_naive` | 12 | 36 | 3 | 0 | 0 | 24 | 12 | 0 |
| `avg_wide` | 12 | 120 | 10 | 0 | 0 | 108 | 12 | 0 |
| `avg_shift` | 12 | 84 | 7 | 0 | 0 | 72 | 12 | 0 |
| `avg_bits` | 12 | 60 | 5 | 0 | 0 | 48 | 12 | 0 |
| `avg_loop`（n=16） | 1 | 194 | 194 | 32 | 16 | 128 | 1 | 17 |
| `_start` | 1 | 277 | 277 | 111 | 0 | 32 | 61 | 64 |
| **合計** | | **771** | | **143** | **16** | **412** | **110** | **81** |

同樣的 12 次計算：

- `avg_bits` 比 `avg_wide` 少 **60 條（−50%）**
- `avg_bits` 比 `avg_shift` 少 **24 條（−28.6%）**
- 但 `avg_bits` 比（錯的）`avg_naive` 多 **24 條（+67%）**——正確性是有代價的

### 3.4 分支數

| 項目 | 分支（beq/bne/blt/bge/bltu/bgeu） | 跳躍（jal/jalr） |
|---|---:|---:|
| 四個純量實作（各 12 次呼叫） | **0** | 48（每次 `ret` 1 條） |
| `avg_loop`（n=16） | 17（1 次 `beqz` + 16 次 `bnez`） | 1（`ret`） |
| `_start` | 64 | 61 |
| **合計** | **81** | **110** |

四個純量實作都是直線程式，**分支數為 0**；唯一的控制流是 `ret`（`jalr`）。
`avg_loop` 的分支密度 = 17 / 194 = **8.8%**，每個元素固定付出 1 條 `bnez`。

### 3.5 每元素成本與 CP3 的意義

`avg_loop` 每元素 12 條：

| 類別 | 條數 |
|---|---:|
| load（2 個輸入） | 2 |
| **AVG 本體（and/xor/srai/add）** | **4** |
| store（1 個輸出） | 1 |
| 迴圈 overhead（4 個 `addi`） | 4 |
| 分支（`bnez`） | 1 |

也就是說，把 AVG 換成一條自訂指令，理論上每元素只能省下 **4 條**（12 → 8，−33%），
剩下的 8 條是記憶體存取與迴圈控制，**自訂指令救不到**。CP3 的指令數比較表必須
把這個「本體 vs 周邊」的比例講清楚，否則容易高估自訂指令的效益。

另一個觀察：如果資料已經在暫存器裡（例如 unrolled 迴圈），純量版的成本就是
`avg_bits` 的 4 條 ALU（`ret` 也被展開掉時），此時 1 條 AVG 的效益是 4 倍。
CP3 會用這兩個情境分別列表。

### 3.6 假設與限制

- 只報**指令數**，不報 cycle 數（§5.4：pipeline 尚未教授）。
- 動態指令數包含函式 `ret`，不包含呼叫端的 `jal`；四個實作都一致，可直接相比。
- `_start` 的數字會隨測試程式改動而變，不具比較意義，僅供完整性。
- 模擬器只支援 `test_avg.S` 用到的指令子集，不是完整 RV32IM。
- CP1 的 C baseline 與 Python `//` 已在 CP1 驗證過 121 組邊界值，此處沿用其語意。

## 4. 遭遇的問題與解法

**問題 1（最重要）：以為 `sltu` 的進位就是 33-bit 和的符號位。**

第一版 `avg_carry` 是這樣寫的：

```asm
        add   t0, a0, a1
        sltu  t1, t0, a0        # 進位
        srli  a0, t0, 1
        slli  t1, t1, 31
        or    a0, a0, t1
```

跑 `avg_carry(-10, 3)` 得到 **2147483644**，正確是 **−4**。

原因：`sltu` 給的是**無號加法**的進位，只有 `a+b ≥ 2^32` 才會是 1；
但 33-bit 和的符號位是「和是否為負」。`−10 + 3 = −7` 沒有無號進位，符號位卻是 1。
反過來 `INT_MAX + INT_MAX` 的符號位是 0，但低 32 位看起來像負數。
所以單靠進位（或單靠 32 位結果的符號位）都無法還原第 33 位。

解法有三個層次，我們都留下來當教學對照：

1. `avg_wide`：把兩個運算元的符號位（`srai 31`）也加進高位字，`hi = sa + sb + carry`。
2. `avg_shift`：不要產生 33-bit 中間值，把每個運算元各自拆成「商 + 餘數」。
3. `avg_bits`：利用 `(a+b) = (a&b) + (a^b)` 讓 `(a^b)` 這一項不產生進位。

**問題 2：C 的 `/` 向 0 截斷，不是 floor。**

CP1 已處理（負奇數補 1）。組合語言反而簡單：`srai` 定義上就是往 −∞ 取整，
所以 `avg_shift`、`avg_bits` 直接得到 floor，不需要補正。
唯一要小心的是不能對「已溢位的 32 位和」做 `srai`——這正是 `avg_naive` 的錯。

**問題 3：本機沒有 RISC-V 工具鏈，怎麼量指令數？**

沒有 `riscv64-elf-gcc`、沒有 `objdump`，也沒有 C 編譯器。做法是寫一支
`rv32im_sim.py`（組譯器 + 指令階層模擬器），直接組譯並執行 `.S`。
為了避免「模擬器遷就自己的程式」，做了三件事：

1. `--selftest`：用 9 條已知機器碼驗證編碼器。
2. 模擬器**解碼機器碼**而不是執行 AST，編碼錯會直接算錯。
3. 300 組隨機／邊界測資與 Python `//` 對照。

最後應在 Ripes 手動載入 `test_avg.S` 做交叉驗證（預期結束時 `a0 = 0`、`s2 = 2`）。
**這一步尚未執行**，列為繳交前待辦（見 §3.6）。

## 5. 白話說明（200 字內）

兩個 32 位整數相加，結果可能多出第 33 位，直接丢掉就會算錯。我們先把加法拆成
「兩數都有的位」（`a & b`）和「兩數不同的位」（`a ^ b`）：不同的位相加永遠不會進位，
所以可以先除以 2 再相加。這樣完全不需要 33 位，五條指令就完成，而且因為用的是
算術右移，負數自動往小的方向取整。

卡住最久的是：一開始以為「加法有沒有進位」就等於「結果是正是負」，但 `−10 + 3`
沒有進位、結果卻是負的，測試立刻抓到。修正後才發現，真正該問的不是「怎麼存第 33 位」，
而是「怎麼讓它根本不要出現」。
